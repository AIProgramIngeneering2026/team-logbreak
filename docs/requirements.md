# Требования LogBreak

## Термины

- **Job** — задание на анализ одного набора логов.
- **Analyzer** — исполнитель, который реализует единый контракт анализа.
- **Отчёт** — объединённый результат всех выбранных анализаторов.

## Сценарий 1. Запустить анализ логов

**Цель:** получить отчёт о найденных проблемах.

**Участник:** разработчик или инженер поддержки.

**Основной поток:**

1. Пользователь отправляет текстовый файл логов и список анализаторов.
2. Сервис проверяет формат и размер входных данных.
3. Сервис создаёт Job и возвращает его идентификатор.
4. Dispatcher запускает выбранные анализаторы через Registry.
5. Сервис объединяет результаты и переводит Job в состояние `completed`.
6. Пользователь получает отчёт с находками, серьёзностью и рекомендациями.

**Критерии приёмки:**

- Дано: корректный файл логов и существующие анализаторы. Когда: пользователь создаёт Job. Тогда: API возвращает `202 Accepted`, идентификатор и состояние `queued`.
- Дано: Job успешно обработан всеми анализаторами. Когда: пользователь запрашивает результат. Тогда: API возвращает состояние `completed` и отчёт с результатом каждого анализатора.
- Дано: повторный запрос с тем же ключом идемпотентности и тем же телом. Когда: пользователь создаёт Job. Тогда: сервис возвращает ранее созданный Job и не запускает повторный анализ.

## Сценарий 2. Проверить состояние и получить результат

**Цель:** понять, завершилось ли задание, и забрать отчёт.

**Участник:** пользователь API.

**Основной поток:**

1. Пользователь запрашивает Job по идентификатору.
2. Сервис загружает Job из хранилища.
3. Сервис возвращает текущее состояние и доступные метаданные.
4. Для завершённого Job сервис также возвращает отчёт.

**Критерии приёмки:**

- Дано: Job находится в состоянии `queued` или `running`. Когда: запрошено его состояние. Тогда: API возвращает актуальное состояние без итогового отчёта.
- Дано: Job находится в состоянии `completed`. Когда: запрошен его результат. Тогда: API возвращает отчёт и время завершения.

## Сценарий 3. Отменить анализ

**Цель:** прекратить ненужную обработку.

**Участник:** пользователь, создавший Job.

**Основной поток:**

1. Пользователь отправляет запрос отмены.
2. Сервис проверяет текущее состояние Job.
3. Для `queued` или `running` сервис останавливает дальнейшую обработку.
4. Job переходит в состояние `cancelled`.

**Критерии приёмки:**

- Дано: Job находится в `queued`. Когда: пользователь отменяет его. Тогда: Job переходит в `cancelled`, анализаторы не запускаются.
- Дано: Job находится в `completed`, `failed` или `cancelled`. Когда: пользователь пытается отменить его. Тогда: API возвращает ошибку `invalid_state_transition`, состояние не меняется.

## Сценарий 4. Отклонить некорректные входные данные (ошибочный)

**Цель:** не создавать заведомо невыполнимое задание.

**Участник:** пользователь API.

**Основной поток:**

1. Пользователь отправляет пустой, слишком большой или неподдерживаемый файл.
2. Сервис проверяет входные данные до создания Job.
3. Сервис отклоняет запрос и возвращает структурированную ошибку.

**Критерии приёмки:**

- Дано: пустой файл. Когда: пользователь создаёт Job. Тогда: API возвращает `422` и код `empty_log`, Job не создаётся.
- Дано: файл превышает настроенный лимит. Когда: пользователь создаёт Job. Тогда: API возвращает `413` и код `payload_too_large`, Job не создаётся.
- Дано: указан неизвестный анализатор. Когда: пользователь создаёт Job. Тогда: API возвращает `422` и код `unknown_analyzer` со списком неизвестных имён.

## Сценарий 5. Пережить сбой каталога сигнатур (ошибочный)

**Цель:** завершить обработку предсказуемо при недоступности внешней зависимости.

**Участник:** пользователь API; внешний каталог сигнатур ошибок.

**Основной поток:**

1. Анализатор запрашивает актуальные сигнатуры у внешнего HTTP-сервиса.
2. Адаптер прерывает зависший запрос по timeout.
3. Адаптер выполняет ограниченное число повторов с задержкой.
4. После исчерпания попыток анализатор возвращает контролируемую ошибку.
5. Job переходит в `failed`, а причина сохраняется в едином формате.

**Критерии приёмки:**

- Дано: каталог не отвечает дольше настроенного timeout. Когда: исчерпаны разрешённые повторы. Тогда: Job переходит в `failed` с кодом `signature_catalog_unavailable`.
- Дано: каталог вернул некорректный JSON. Когда: адаптер разбирает ответ. Тогда: повтор не выполняется, Job переходит в `failed` с кодом `invalid_dependency_response`.
- Дано: используется fake-каталог в тестах. Когда: он имитирует timeout или мусорный ответ. Тогда: результат не зависит от реальной сети и воспроизводится при каждом запуске.

## Жизненный цикл Job

Состояния:

- `created` — запрос принят и Job сохранён;
- `queued` — Job прошёл проверку и ожидает выполнения;
- `running` — Dispatcher выполняет анализаторы;
- `completed` — все анализаторы успешно вернули результат;
- `failed` — обработка завершилась контролируемой ошибкой;
- `cancelled` — пользователь отменил незавершённый Job.

Разрешённые переходы:

- `created → queued`;
- `created → failed`;
- `queued → running`;
- `queued → cancelled`;
- `running → completed`;
- `running → failed`;
- `running → cancelled`.

Состояния `completed`, `failed` и `cancelled` терминальные. Любой неуказанный переход отклоняется с ошибкой `invalid_state_transition`.

## Что предложил ИИ

**Промпт:**

> Мы проектируем сервис анализа логов. Основной сценарий: пользователь загружает лог, сервис создаёт Job, запускает выбранные анализаторы и возвращает отчёт. Найди ещё три способа сломать этот сценарий. Для каждого опиши ожидаемое безопасное поведение сервиса.

### 1. Повторная отправка после сетевого timeout

**Предложение:** клиент не получил ответ и повторил создание Job, из-за чего анализ запускается дважды.

**Решение:** принято. Для `POST /jobs` вводится ключ идемпотентности. Одинаковый ключ и тело возвращают существующий Job; тот же ключ с другим телом даёт конфликт.

### 2. Лог содержит секреты или персональные данные

**Предложение:** пользователь случайно отправил токен, пароль или адрес электронной почты.

**Решение:** принято частично. В первой версии сервис не обещает надёжно распознавать все виды секретов, поэтому явно запрещает такие данные, не пишет исходный лог в прикладные логи и ограничивает срок хранения. Автоматическая маскировка вынесена в backlog.

### 3. Один анализатор вернул слишком большой результат

**Предложение:** неисправный анализатор исчерпал память или сделал итоговый ответ непригодным для передачи.

**Решение:** принято. Контракт Analyzer ограничивает размер результата и число находок. Нарушение считается ошибкой анализатора и переводит Job в `failed`; частичный непроверенный отчёт пользователю не выдаётся.
