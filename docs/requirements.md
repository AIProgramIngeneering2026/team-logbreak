# Требования IndieFashion Radar

## Термины

- **Collection Job** — задание на сбор и нормализацию данных из выбранных источников.
- **Source Adapter** — исполнитель, который получает публикации одного типа источника по единому контракту.
- **Fashion Item** — нормализованная карточка публикации или товара со ссылкой на оригинал.
- **Trend Summary** — сводка по категориям, цветам, материалам и диапазонам цен за период.

## Сценарий 1. Запустить сбор публикаций

**Цель:** получить свежие публикации и товары небольших модных брендов из выбранных источников.

**Участник:** стилист, покупатель или исследователь моды.

**Основной поток:**

1. Пользователь выбирает настроенные Telegram-каналы и сайты, а также период сбора.
2. Сервис проверяет источники, лимиты и параметры запроса.
3. Сервис создаёт Collection Job и возвращает его идентификатор.
4. Dispatcher выбирает подходящие Source Adapter через Registry.
5. Адаптеры получают только новые публичные публикации.
6. Сервис нормализует записи, удаляет дубликаты и сохраняет результат с указанием источника.
7. Job переходит в состояние `completed`, а пользователь получает ссылку на результат.

**Критерии приёмки:**

- Дано: два разрешённых источника и корректный период. Когда: пользователь создаёт Collection Job. Тогда: API возвращает `202 Accepted`, идентификатор и состояние `queued`.
- Дано: адаптеры успешно получили публикации. Когда: обработка завершается. Тогда: каждая Fashion Item содержит бренд, тип источника, дату, ссылку на оригинал и доступные атрибуты.
- Дано: одна публикация встретилась в нескольких выдачах. Когда: сервис нормализует результаты. Тогда: сохраняется одна карточка со всеми известными ссылками на происхождение.
- Дано: повторный запрос с тем же ключом идемпотентности и тем же телом. Когда: пользователь создаёт Job. Тогда: сервис возвращает ранее созданный Job и не запускает повторный сбор.

## Сценарий 2. Найти и отфильтровать собранные данные

**Цель:** найти подходящие товары и публикации среди результатов сбора.

**Участник:** покупатель, стилист или автор тематического канала.

**Основной поток:**

1. Пользователь задаёт один или несколько фильтров: бренд, категория, цена, материал, источник или дата.
2. Сервис проверяет параметры и строит запрос к хранилищу.
3. Сервис возвращает страницу Fashion Item с краткими данными и ссылками на оригиналы.
4. Пользователь открывает следующую страницу по непрозрачному курсору.

**Критерии приёмки:**

- Дано: в хранилище есть карточки разных брендов. Когда: пользователь фильтрует по бренду и диапазону цены. Тогда: ответ содержит только подходящие карточки и общее число найденных результатов.
- Дано: у публикации отсутствует цена. Когда: пользователь не задал фильтр цены. Тогда: публикация остаётся в выдаче, а поле цены имеет значение `null`.
- Дано: результатов больше размера страницы. Когда: пользователь передаёт курсор следующей страницы. Тогда: элементы не повторяются и не пропускаются.

## Сценарий 3. Получить сводку тенденций

**Цель:** понять, какие категории, цвета, материалы и диапазоны цен чаще встречались за выбранный период.

**Участник:** стилист, небольшой бренд или исследователь моды.

**Основной поток:**

1. Пользователь задаёт период и необязательный список брендов.
2. Сервис выбирает нормализованные Fashion Item за период.
3. Сервис подсчитывает частоты атрибутов и долю записей с неполными данными.
4. Сервис возвращает Trend Summary и ссылки на примеры публикаций.

**Критерии приёмки:**

- Дано: за период собрано достаточно карточек. Когда: пользователь запрашивает сводку. Тогда: API возвращает наиболее частые категории, цвета, материалы и ценовые диапазоны с количеством наблюдений.
- Дано: часть карточек не содержит цвета или материала. Когда: строится сводка. Тогда: пропуски не считаются отдельным трендом, а их доля указывается в качестве данных.
- Дано: за период нет карточек. Когда: запрошена сводка. Тогда: API возвращает пустые списки и нулевое количество наблюдений без выдуманных выводов.

## Сценарий 4. Отклонить запрещённый или некорректный источник (ошибочный)

**Цель:** не собирать закрытые данные и не нарушать ограничения источника.

**Участник:** пользователь API.

**Основной поток:**

1. Пользователь передаёт адрес источника.
2. Сервис проверяет тип адреса, наличие источника в списке разрешённых и правила доступа.
3. Сервис отклоняет закрытый, неподдерживаемый или запрещающий сбор источник.
4. Пользователь получает структурированную ошибку; Job не создаётся.

**Критерии приёмки:**

- Дано: адрес закрытого Telegram-канала. Когда: пользователь пытается добавить источник. Тогда: API возвращает `422` и код `private_source_not_allowed`.
- Дано: сайт запрещает автоматический доступ для нашего клиента. Когда: источник проходит проверку. Тогда: API возвращает `403` и код `collection_not_allowed`.
- Дано: адрес не относится ни к одному поддерживаемому типу источника. Когда: пользователь добавляет его. Тогда: API возвращает `422` и код `unsupported_source`.
- Дано: источник отклонён. Когда: проверяется хранилище. Тогда: для него нет ни Job, ни сохранённого содержимого.

## Сценарий 5. Завершить сбор при сбое части источников (ошибочный)

**Цель:** вернуть полезный частичный результат, если один источник временно недоступен.

**Участник:** пользователь API; публичный Telegram-канал или сайт бренда.

**Основной поток:**

1. Dispatcher запускает адаптер для каждого выбранного источника.
2. Один адаптер получает timeout, ответ `429` или некорректный документ.
3. Адаптер соблюдает `Retry-After` либо выполняет ограниченный повтор с задержкой.
4. После исчерпания попыток ошибка источника сохраняется отдельно.
5. Если хотя бы один источник обработан, Job переходит в `partial`; если не обработан ни один — в `failed`.
6. Пользователь получает результаты успешных источников и список отказов без технических секретов.

**Критерии приёмки:**

- Дано: один из трёх источников не отвечает. Когда: остальные два обработаны успешно. Тогда: Job переходит в `partial`, а их карточки доступны пользователю.
- Дано: источник вернул `429` с `Retry-After`. Когда: адаптер планирует повтор. Тогда: он ждёт указанное время и не превышает настроенное число попыток.
- Дано: сайт вернул документ неожиданной структуры. Когда: адаптер не может безопасно разобрать его. Тогда: причина имеет код `invalid_source_response`, а сырой документ не попадает в пользовательский ответ.
- Дано: fake-источник имитирует timeout, `429` или некорректный ответ. Когда: запускаются интеграционные тесты. Тогда: результат воспроизводится без обращения к реальным каналам и сайтам.

## Жизненный цикл Job

Состояния:

- `created` — запрос принят и Job сохранён;
- `queued` — источники проверены, Job ожидает выполнения;
- `collecting` — адаптеры получают публикации из внешних источников;
- `processing` — сервис нормализует данные и удаляет дубликаты;
- `completed` — все выбранные источники обработаны успешно;
- `partial` — часть источников обработана, часть завершилась ошибкой;
- `failed` — ни один источник не дал пригодного результата;
- `cancelled` — пользователь отменил незавершённый Job.

Разрешённые переходы:

- `created → queued`;
- `created → failed`;
- `queued → collecting`;
- `queued → cancelled`;
- `collecting → processing`;
- `collecting → failed`;
- `collecting → cancelled`;
- `processing → completed`;
- `processing → partial`;
- `processing → failed`;
- `processing → cancelled`.

Состояния `completed`, `partial`, `failed` и `cancelled` терминальные. Любой неуказанный переход отклоняется с ошибкой `invalid_state_transition`.

## Что предложил ИИ

**Промпт:**

> Мы проектируем агрегатор публичной информации о небольших модных брендах. Основной сценарий: пользователь выбирает Telegram-каналы и сайты, сервис создаёт Collection Job, получает публикации через адаптеры, нормализует их и возвращает подборку. Найди ещё три способа сломать этот сценарий. Для каждого опиши ожидаемое безопасное поведение сервиса.

### 1. Один товар опубликован в нескольких источниках

**Предложение:** Telegram-канал бренда и его сайт содержат одну и ту же карточку, поэтому выдача заполняется дубликатами.

**Решение:** принято. Сервис вычисляет нормализованный ключ по бренду, ссылке, артикулу и доступным атрибутам. Явные совпадения объединяются, а неоднозначные записи остаются раздельными, чтобы не потерять товары ошибочно.

### 2. Источник изменил HTML или формат ответа

**Предложение:** адаптер продолжает работать, но начинает записывать перепутанные цены и названия.

**Решение:** принято. Результат адаптера проверяется схемой и контрольными ограничениями. При массовом нарушении схемы данные источника не публикуются, источник получает ошибку `invalid_source_response`, а тесты используют сохранённые обезличенные примеры документов.

### 3. Telegram или сайт ограничил частоту запросов

**Предложение:** параллельный сбор вызывает `429`, временную блокировку или лишнюю нагрузку на небольшой бренд.

**Решение:** принято. Для каждого домена и канала действует отдельный лимит запросов. Адаптер учитывает `Retry-After`, применяет ограниченный retry с задержкой и использует время последнего успешного сбора, чтобы не запрашивать старые публикации повторно.
